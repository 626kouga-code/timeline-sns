## ログ・監視・エラー通知

### 全体像

ログ監視は次の 3 段階で考える。①はアプリ側で実装し（#65）、②と③は AWS 構築（#6）のときに作る。フロントエンドのエラーは監視しない。

| 段階 | やること | 手段 |
| --- | --- | --- |
| ① 出す | 何を、どのレベルで、どの形式で出すかを決める | Spring Boot の構造化ログ（JSON）、リクエスト ID、ヘルスチェック |
| ② 集める | サーバーのログを 1 か所に送って保管する | CloudWatch Logs（保持 14 日） |
| ③ 気づく | 異常を数値にして、しきい値を超えたら通知する | メトリクスフィルタ → CloudWatch アラーム → Amazon SNS のメール |

### ① ログの出力方針（アプリ側）

**形式**

- 本番では JSON 形式で標準出力に出す。Spring Boot 標準の構造化ログ（`logging.structured.format.console: ecs`）を使い、ライブラリは追加しない
- ローカルとテストでは、これまでどおりテキスト形式にする（プロファイルで切り替える）
- JSON の項目名は ECS（Elastic Common Schema）に従う。レベルは `log.level`、メッセージは `message`、時刻は `@timestamp` に入る

**レベルの基準**

| レベル | 使う場面 | 例 |
| --- | --- | --- |
| ERROR | 想定外のことが起き、対応が必要 | 500 になる未処理の例外（スタックトレース付き） |
| WARN | 想定内だが、続くようなら調べる | 画像の削除失敗、リフレッシュトークンの再利用検知 |
| INFO | 1 リクエストにつき 1 行のアクセスログ、重要な出来事 | アクセスログ、起動・停止 |
| DEBUG | ローカルだけで使う | 処理の途中経過 |

本番のレベルは `com.timelinesns` も含めて INFO とする。

**全ログに付ける項目**

- `requestId`：リクエストごとに振る ID。同じリクエストで出たログをまとめて追うのに使う
- `userId`：ログイン中のリクエストだけ

**アクセスログ**（INFO、1 リクエストにつき 1 行）

| 項目 | 内容 |
| --- | --- |
| `method` | HTTP メソッド |
| `path` | パス。クエリ文字列は含めない |
| `status` | レスポンスのステータスコード |
| `durationMs` | 処理時間（ミリ秒） |

`/actuator/health` へのアクセスはログに出さない（ヘルスチェックの数だけ行が増えるため）。

**リクエスト ID**

- Filter で `X-Request-Id` ヘッダを受け取る。なければ UUID を振る
- MDC に入れて全ログに付け、レスポンスの `X-Request-Id` ヘッダでも返す
- 500 エラーの ProblemDetail にも `requestId` を入れる。利用者から「エラーになった」と連絡があれば、この ID でログを検索する

**例外**

- `ApiExceptionHandler` に、想定外の例外（`Exception`）をすべて受ける処理を追加する。ERROR をスタックトレース付きで出し、500 の ProblemDetail（`code: INTERNAL_ERROR`）を返す。例外のメッセージはレスポンスに含めない
- 4xx はアクセスログだけにし、ERROR は出さない。利用者の入力ミスでアラームが鳴らないようにするため

**ログに出さない情報**

- パスワード、アクセストークン、リフレッシュトークン
- `Authorization` ヘッダ、Cookie
- メールアドレス、投稿やコメントの本文
- リクエストボディそのもの

**ヘルスチェック**

- Spring Boot Actuator を導入し、公開するのは `/actuator/health` だけにする（DB に接続できるかも含む）
- 応答は `UP` / `DOWN` だけにし、詳細は返さない

**今回は入れないもの**

- アプリのメトリクス（Micrometer）、分散トレーシング、フロントエンドのエラー送信。利用者が数十人の規模では、ログとインフラのメトリクスだけで足りるため

### ② 収集（CloudWatch Logs）

- ロググループは `/timeline-sns/backend` とし、保持期間は 14 日にする
- ログの送り方は AWS 構成によって変わる
  - EC2 で動かす場合：Docker の `awslogs` ログドライバ、または CloudWatch Agent で送る。ディスク使用率も CloudWatch Agent で送る
  - ECS で動かす場合：タスク定義で `awslogs` ログドライバを指定する
- 料金：取り込みが月 5GB までなら無料枠に収まる。アクセスログ 1 行を約 500 バイトとすると、1 日 1 万リクエストでも月 150MB ほど

### ③ 検知（メトリクスフィルタとアラーム）

ログの件数はメトリクスフィルタで数値にしてから、アラームを付ける。通知先は SNS トピック `timeline-sns-alarms` にし、管理者のメールアドレスを登録する。

| 監視項目 | 元のデータ | 条件の目安 |
| --- | --- | --- |
| 5xx エラーの増加 | メトリクスフィルタ `{ $.status >= 500 }` | 5 分間に 5 件以上 |
| ERROR ログ | メトリクスフィルタ `{ $.log.level = "ERROR" }` | 5 分間に 1 件以上 |
| CPU 使用率 | EC2 / ECS の標準メトリクス | 80% 超が 10 分続く |
| DB 接続数 | RDS の `DatabaseConnections`（DB を同居させる場合は CloudWatch Agent で取る） | 上限の 80% 超 |
| ディスク使用率 | CloudWatch Agent の `disk_used_percent`（EC2 の場合） | 80% 超 |
| ヘルスチェック | `/actuator/health` を外から見る。ALB があれば ALB のヘルスチェック、なければ Route 53 のヘルスチェックを使う | 2 回続けて失敗 |
| 料金 | AWS Budgets | 月額予算の 80%・100% |

- アラームが「回復（OK）」になったときも通知する。鳴ったままなのか、もう収まったのかを判断できるようにするため
- しきい値は運用しながら調整する。鳴りすぎるアラームは無視されるようになるので、すぐ見直す

### アラームが鳴ったときの対応

1. 通知メールで、どのアラームが鳴ったかを確認する
2. CloudWatch Logs Insights で、その時刻前後の ERROR を探す

    ```text
    fields @timestamp, requestId, message, error.stack_trace
    | filter log.level = "ERROR"
    | sort @timestamp desc
    | limit 50
    ```

3. 見つけた `requestId` で検索し、同じリクエストのログをまとめて見る
4. 再起動するか、直前のデプロイを戻すかを判断する。原因と対応は Issue に残す

## バックアップ

- RDS を使う場合：自動バックアップを有効にし、保持期間は 7 日とする
- EC2 に DB を同居させる場合：毎日 pg_dump でバックアップを取り、S3 に保存する。S3 のライフサイクル設定で 7 日後に自動削除する
- 投稿画像の S3 バケットはバージョニングを有効にし、誤削除に備える
- 公開前に一度、バックアップからの復元手順を実際に試す
